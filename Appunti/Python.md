## Introduzione
Python è un linguaggio di programmazione interpretato, ovvero in cui il codice non viene prima tradotto interamente in linguaggio macchina, ma le singole istruzioni vengono eseguite, dall'interprete Python (CPython), riga per riga. Ciò che fa CPython è tradurre il codice in un "byte code" (file .pyc), ovvero uno codice generato appositamente per una macchina virtuale, la PVM (Python Virtual Machine).
Python, in quanto orientato agli oggetti, manipola i cosiddetti data objects, ovvero oggetti che hanno un tipo, che può essere scalare e non-scalare, dove per non-scalare si intendono oggetti con una struttura interna accessibile. Le stringhe sono tipi di oggetti particolari, che sono per definizione non-scalari (dato che sono letteralmente array di caratteri), ma vengono trattati come scalari (non si può modificare con una normale assegnazione un singolo carattere di una stringa).
Una funzione in Python è composta da nome, parametri, docstring opzionale, corpo e valore di ritorno (se non specificato, una funzione in Python ritorna sempre None).
Per scope di una variabile si intende il mapping tra il nome della variabile e l'oggetto a cui punta, che può cambiare in base alla funzione in esecuzione. 

## Moduli e Package
In Python le definizioni di funzioni e variabili non sono salvate all'uscita dell'interprete, quindi arrivano in nostro soccorso i moduli, che permettono di eseguire istruzioni come script eseguibili (infatti sono proprio dei normali file .py), importandoli tramite keyword import (nel momento in cui l'interprete esegue l'import, vengono eseguite tutte le dichiarazione e definizioni del modulo importato). Per definire delle funzionalità di un modulo che non vanno eseguite all'importazione, queste si possono inserire nella variabile globale \_\_main\_\_, così che vengano eseguite solo quando è il modulo stesso ad essere eseguito dall'utente. CPython cerca i moduli importati in determinati luoghi specifici, nel seguente ordine: 
directory corrente -> elenco delle directory nel PYTHONPATH -> percorso predefinito (in base all'installazione).
Esiste anche una libreria standard di moduli Python, in cui sono contenuti moduli che svolgono operazioni importanti ma non facenti parte del nucleo di Python, come ad esempio il modulo sys, che grazie alla sua variabile argv permette di fornire parametri ad un programma python direttamente dall'esecuzione, specificandoli dopo il nome del programma (python programma.py arg1 arg2 ...).
I moduli in Python sono organizzati in Packages, memorizzati in directory, dove ogni directory contiene un file \_\_init.py\_\_, che istruisce l'interprete di trattare la directory come fosse un package e può essere vuoto oppure contenere delle istruzioni di inizializzazione per il package.

## Tuple, Liste e Dizionari
Le strutture dati principali di Python sono Tuple, Liste e Dizionari, indicate rispettivamente con (), 
\[\] e {}.
Le Tuple sono una sequenza **ordinata** di elementi eterogenei che non possono cambiare, quindi una tupla è immutabile. 
Una Lista è una sequenza **ordinata** di informazioni, accessibile tramite indice. Anch'essa può contenere elementi eterogenei, ma non è buona norma farlo. Gli elementi di una lista possono cambiare, quindi è mutabile. Su una lista si possono effettuare varie operazioni: add, extend, remove, sort, reverse...
Dichiarando una  lista, e poi assegnando il nome di questa lista ad un'alta variabile, si va a creare un alias, e ogni modifica fatta sull'alias si andrà a rispecchiare sulla lista originale (e viceversa), se si vuole creare una nuova lista partendo da una già esistente, bisogna usare l'operatore \[\:\].
Il terzo tipo di struttura dati è il Dizionario, ovvero una struttura composta da elementi associati ad un identificativo (una coppia chiave/valore). I valori possono essere di qualsiasi tipo, possono essere duplicati e addirittura possono essere altre strutture dati (un dizionario di dizionari è possibile), mentre le chiavi devono essere uniche ed immutabili. Né le chiavi né i valori sono ordinati.

## Parametri
In Python tutto è un oggetto, con cui si può interagire tramite i riferimenti, e ciò vale anche per il passaggio di parametri: passando un parametro ad una funzione, il riferimento contenuto nel parametro attuale è copiato in quello formale, e se si tratta di un oggetto mutabile, ogni modifica del parametro formale si riflette su quello attuale.
Per passare un numero variabile di argomenti si può dichiarare tra i parametri nella firma della funzione il parametro \*args (dev'essere l'ultimo parametro della firma), Inoltre, è possibile per il chiamante specificare quale parametro attuale rappresenta quale parametro formale tramite i keyword arguments, ed inoltre è possibile usare il parametro \*\*kwargs per passare un numero variabile di di keyword arguments.

## File e Eccezioni
Quando viene eseguito un programma Pyhon si creano 3 oggetti file: sys.stdin, sys.stdout e sys.stderr; che rappresentano i flussi di dati standard che collegano il programma al terminale.
E' possibile utilizzare l'istruzione with per acquisire risorse e rilasciarle automaticamente al termine del loro utilizzo, questa può essere usata sia per file che per lock.
Le funzioni principali sui file sono open, write, readlines e seek.
Per gestire i file si fa uso del modulo os, che permette di creare, rimuovere e rinominare file del filesystem.
Quando una funzione produce delle condizioni non attese si genera un'eccezione, le eccezioni possono essere gestite tramite blocco try/except/else/finally. Si può anche sollevare un'eccezione manualmente tramite l'istruzione raise. Infine, si possono usare le asserzioni per essere sicuri che l'esecuzione sia come attesa, quindi si può usare l'istruzione assert, che verifica la condizione attesa e se fallisce solleva un AssertionError.

## OOP
Python è Object-Oriented, quindi ogni tipo di dato rappresenta una classe. Gli oggetti possono essere istanziati, manipolati e distrutti (esplicitamente o lasciando il compito al garbage collector).
Una classe può essere implementata tramite la keyword class, seguita da nome e eventuali relazioni con altre classi. I dati e le procedure che appartengono ad una classe sono detti attributi e metodi. Il costruttore in Python è un metodo chiamato \_\_init\_\_, che prende come primo parametro self, che rappresenta l'istanza della classe.
Un altro metodo particolare è \_\_str\_\_ che è utilizzato per permettere l'uso di un oggetto di una classe in una print. Ci sono molti altri metodi che si possono overridare per adattare il comportamento di altri operatori speciali, come \_\_add\_\_ per la somma o \_\_eq\_\_ per l'uguaglianza.
Altri metodi importanti sono i getter e setter che sono utilizzati per implementare il concetto di information hiding all'interno del programma.
Una superclasse è una classe da cui altre classi, le sottoclassi, ereditano attributi e metodi. Una sottoclasse può ereditare da più superclassi (ereditarietà multipla), ma questa possibilità introduce un problema noto come il Diamond Problem: se una classe eredita da due classi che overloadano lo stesso metodo di una superclasse, quale metodo verrà usato se invocato dalla prima classe? Python risolve il problema dando la priorità in base all'ordine di ereditarietà.
Le classi in Python possono anche avere delle variabili statiche, ovvero condivise tra tutte le istanze della classe. I metodi statici invece sono metodi di una classe che possono essere invocati senza averne istanziato un oggetto.
In Python ogni eccezione è un oggetto della classe BaseException (o di una classe che eredita da quella, tra cui le quattro principali sottoclassi ovvero SystemExit, KeyboardInterrupt, GeneratorExit e Exception).
Il polimorfismo in Python consente di avere sottoclassi con metodi omonimi alle superclassi, lasciando poi all'interprete il compito di scegliere il più adatto a run-time. La caratteristica principale è che consente ciò è il duck typing (un tipo di tipizzazione dinamica), che fa uso di late binding e dynamic dispatch per identificare di che tipo è un oggetto, in base alla presenza di metodi o di proprietà varie.
Una classe che contiene almeno un metodo astratto (ovvero un metodo senza implementazione, quindi solo la firma) è detta classe astratta, mentre se tutti i metodi sono astratti, allora è un'interfaccia. Le classi astratte (e quindi le interfacce) non possono essere istanziate, ma sono solo dei "modelli" per altre classe che ereditano da esse. In Python l'infrastruttura che definisce il comportamento di una classe astratta è data dal modulo abc, che va sempre ereditato da qualsiasi classe astratta. Di questo modulo bisogna anche usare il decoratore @abc.abstractmethod per indicare che un metodo è astratto.
Per quanto riguarda le interfacce, ci sono due approcci principali, informale e formale. Le interfacce informali sono quelle più semplici che sfruttano la natura dinamica di Python per definire metodi astratti da overridare, ma senza obbligare le sottoclassi ad effettuare questo overriding; un'interfaccia formale invece sfrutta anch'essa l'eredità da abc e il decoratore @abc.abstractmethod per obbligare le sottoclassi ad effettuare l'overriding di tutti i metodi.

## Programmazione Concorrente
In Python abbiamo a disposizione due moduli per gestire al concorrenza: threading e multiprocessing.
Il modulo threading fornisce un'interfaccia di alto livello per il multihtreading, tramite varie classi, ad esempio la classe Thread, le cui istanze rappresentano un flusso di controllo separato da quello principale (il Main Thread). I due metodi principali di creare un Thread sono istanziando direttamente un oggetto di Thread (passando un callable object come parametro) oppure creando una classe che estende Thread e overrida il metodo run(). Un thread può essere contrassegnato come daemon, e ciò vuol dire che il programma principale non dovrà attendere che esso si concluda per terminare, ma verrà interrotto automaticamente alla terminazione del processo padre. E' possibile usare la classe local per definire degli attributi di un oggetto thread i cui valori sono esclusivi al singolo thread in esecuzione, nonostante condivida lo spazio di memoria con il padre e i fratelli.
Per la sincronizzazione viene utilizzata la classe Lock, i cui oggetti possono trovarsi in uno di due stati: locked o unlocked. Di base è unlocked, ma quando un thread lo acquisisce diventa locked, tornando unlocked al momento del rilascio.
Per gestire l'acquisizione e il rilascio si possono o usare le primitive acquire e release oppure, preferibilmente, lo statement with.
Un'alternativa al Lock è il RLock, ovvero Reentrant Lock, che può essere acquisito più volte dallo stesso thread, avendo a differenza di un Lock classico anche una memoria su chi l'ha acquisito è in grado di "accettare" la riacquisizione da parte dello stesso thread (incrementando un contatore interno che indica il numero di acquisizioni), è utile per gestire il problema del self-deadlock.
La classe Condition implementa una condition variable, ovvero un oggetto che rappresenta una condizione che uno o più thread possono controllare e restare in attesa finchè essa non si verifica (ovvero finchè non vengono notificati da un altro thread). Ad ogni cv è associato un Lock (che di default è reentrant, ma può anche essere classico). Fornisce i metodi wait, wait_for, notify e notify_all, che rispettivamente mettono i thread in attesa della notifica o della condizione e notificano n o tutti i thread in attesa su quella cv.
La classe Semaphore introduce l'oggetto semaforo, che gestisce un contatore interno che viene decrementato ad ogni acquire e incrementato ad ogni release, e quando arriva a zero blocca il thread chiamante finché non viene incrementato da un altro thread.
La classe Event fornisce un meccanismo di comunicazione tra thread: è possibile istanziare un oggetto event che ha un flag interno che può essere Set o Clear (True o False), e tramite il metodo is_set è possibile controllarne lo stato (oppure porre un thread in attesa del set tramite l'apposita wait).
Python utilizza un meccanismo, noto come Global Interpreter Lock (GIL) per assicurarsi che solo un thread alla volta possa eseguire bytecode, rendendo nell'effettivo l'esecuzione di thread non parallela, creando un grosso collo di bottiglia per i task cpu-bound.
Il modulo multiprocessing supporta lo spawning (in windows, oppure il forking in linux) di processi multipli, aggirando così il problema del GIL (che agisce solo sui thread), dato che crea più processi ognuno con il suo interprete (CPython) e il suo GIL. I metodi principali di avvio di un processo sono spawn, fork e forkserver. Spawn è il default per Windows e MacOS, in cui il padre avvia un nuovo Interpreter Process ed il figlio eredita solo le risorse necessarie ed esegue il metodo run. Fork è il default su Linux, tramite cui il figlio all'avvio eredita tutte le risorse del padre, ma è considerata unsafe dato che duplica solo il flusso di controllo principale del processo, quindi se il padre aveva dei figli con dei lock acquisiti, questi resterano acquisiti da qualcuno anche nel processo figlio, ma non avendo dei thread figli a sua volta, questo lock non potrà mai essere rilasciato (deadlock). Forkserver invece crea un Server Process, a cui il padre si connette quando necessario e richiede ad esso la fork di un processo nuovo, evitando così di ereditare risorse non necessarie e dato che il Server Process è single-thread, l'uso di fork lì è safe.
Esiste un fork del modulo multiprocessing chiamato multiprocess che sostituisce il serializzatore standard (pickle) con dill, permettendo di passare ai processi paralleli callable più complesse, come ad esempio le funzioni lambda.
Un oggetto della classe Process rappresenta un'entità da eseguire in un processo separato, comportandosi allo stesso modo dei Thread di threading, quindi stessa istanziazione e anche multiprocessing fornisce Lock, RLock, Condition, Semaphore ed Event.
Per scambiare oggetti tra processi ci sono due canali di comunicazione principali: Pipe e Queue, dove Pipe consenta la connessione tra più processi e Queue implementa il problema produttori-consumatori. Una Pipe è una coppia di Connection Objects (gli estremi del tubo) e una Queue è una process shared queue, implementata tramite Pipe e Lock (o semafori).
Gli oggetti Connection della Pipe rappresentano gli estremi del tubo e si si possono utilizzare i metodi send e recv, per inviare e ricevere oggetti da un estremo all'altro.
Quando un processo immette un oggetto in una Queue, viene avviato un thread che trasferisce gli oggetti da un buffer alla Pipe usata per implementare la Queue.
Uno degli strumenti offerto dal modulo multiprocessing per la condivisione di dati è la Shared Memory, rappresentata da oggetti di tipo Value o Array (che quindi sono compatibili con il C). 

## Programmazione su Rete
Internet è la grande rete che si estende in tutto il mondo, basata sul protocollo TCP/IP, è una rete di reti, i cui componenti sono: nodi, collegamenti e router. Ad ogni nodo è assegnato un indirizzo IP (IPv4 e IPv6), che servono a trovare mittenti e destinatari. I dati sono trasmessi tramite pacchetti (IP Datagrams) tramite due protocolli principali: TCP e UDP.
Il protocollo TCP è quello affidabile dei due: è orientato alla connessione, fornisce un flusso di byte full duplex e preserva l'ordine dei pacchetti tramite la ritrasmissione di quelli persi. L'UDP invece è non affidabile, proprio come IP, quindi non ha controlli sull'ordine o possibilità di ritrasmissione.
I Socket sono il meccanismo principale di comunicazione su rete tra processi (anche su macchine differenti). Sono caratterizzati da due elementi: IP e Port.
Per creare e usare Socket in Python si usa il modulo socket, i cui metodi principali sono socket, bind, listen, accept, connect e close. Per scambiare dati su socket TCP si usano send e recv: il Client istanzia una Socket e chiede una connessione tramite connect, una volta ricevuta, può scambiare dati tramite send e recv; il Server invece istanzia anch'esso una socket, effettua il bind per legarla ad una porta e si mette in listen aspettando una connessione, quando arriva effettua la accept (che restituisce una socket che rappresenta il Client e l'indirizzo della Socket lato Client) e instaura così il collegamento con il client, potendo quindi scambiare dati tramite send e recv; una volta finito il da farsi, si effettua la close sull'oggetto Socket.
Per la comunicazione UDP con Socket invece si usano sendto e recvfrom: dato che UDP non è connection-oriented non bisogna instaurare la connessione con connect listen e accept, ma il Client effettua direttamente la sendto specificando indirizzo e porta del server e recvfrom, mentre il server deve anche ovviamente fare la bind sulla porta desiderata.
Per migliorare l'efficienza dei Server, questi si possono rendere multi-thread o multi-processo, ricordando che ogni flusso di controllo, thread o processo che sia, deve sempre avere come parametro la connessione restituita dal metodo accept nel caso di Server TCP oppure l'indirizzo e la porta del mittente e il messaggio ricevuto nel caso di Server UDP.
Il pattern Proxy introduce nel modello di interazione Client-Server un Proxy, che rappresenta un'implementazione del servizio remoto, però locale al Client, dove quindi i meccanismi necessari per la comunicazione (TCP o UDP), sono incapsulati all'interno del codice del Proxy.
Un'implementazione del Proxy è nel pattern Proxy-Skeleton, che prevede un Proxy lato client ed uno lato server (lo Skeleton). Saranno questi due proxy a comunicare tra loro, gestendo tutta la logica di comunicazione, lasciando la logica applicativa a client e server. 


## Sistemi Middleware
Un sistema distribuito è un sistema i cui componenti coordinano le loro azioni tramite lo scambio di messaggi, dato che sono su macchine diversi connesse in rete. In generale un sistema distribuito è eterogeneo, e per questo la complessità di sviluppo di software di qualità è molto alta, dato che occorre adoperare tecniche e linguaggi diversi in base all'hardware/software su cui girano i programmi del sistema. Anche i dati sono distribuiti: memorizzati su più archivi e con DBMS diversi. Di norma, è raro trovare sistemi complessi sviluppati da zero: la maggior parte vengono creati a partire da sistemi già funzionanti, facendo uso di COTS e riutilizzo di sistemi legacy. A differenza di come può sembrare, l'integrazione di un sistema esistente è più complessa di uno sviluppo ex-novo, dato che la difficoltà non è la semplice programmazione, ma anche la capacità di adattare componenti già esistenti che magari non erano ideati per interoperare: da qui nascono le tecnologie middleware.
Per middleware si intende uno strato software tra sistema operativo e applicazioni, che fornisce astrazioni e servizi per lo sviluppo di applicazioni distribuite. Un sistema middleware è trasparente rispetto al sistema operativo, dato che opera al di sopra di esso; trasparente rispetto al linguaggio di programmazione, dato che il suo scopo è proprio quello di fare da intermediario tra linguaggio diversi, definendo delle regole non ambigue di corrispondenza con i vari linguaggi; trasparente rispetto alla locazione, dato che è lui a fornire una localizzazione di tutte le risorse del sistema distribuito; trasparente rispetto alla migrazione, dato che può consentire l'accesso a risorse che magari sono state rilocate durante il loro ciclo di vita; trasparente rispetto ai guasti, dato che può offrire al programmatore meccanismi per mascherare i guasti in quanto anche in caso di un singolo fallimento, l'intero sistema distribuito può cedere; trasparente rispetto alla replicazione, dato che questa è una caratteristica fondamentale per la tolleranza ai guasti e la miglioria delle prestazioni. Esistono vari modelli di middleware, quelli che abbiamo visto sono: RPC (SunRPC, gRPC), MOM (JMS, STOMP), DOM (Java RMI) e Web Services (Flask).
Nei sistemi RPC (Remote Procedure Call), la comunicazione è sincrona e bloccante, quindi i processi restano in attesa finché la procedura remota non è completata. Funziona tramite dei metodi di interfaccia chiamati stub (lato client e server) che implementano lo scambio di parametri e la comunicazione su rete. Lo stub client preleva i parametri, li impacchetta e li affida al software di rete, attende la risposta e la spacchetta e infine restituisce i parametri al client. Lo stub server attende che qualcuno invochi la procedura, spacchetta il messaggio ricevuto e lo trasmette alla procedura, impacchetta la risposta della procedura e la invia rimettendosi poi in attesa.
L'impacchettamento e lo spacchettamento sono detti marshalling e unmarshalling; tramite il marshalling si converte il formato dei dati in un formato che sia compreso da entrambe le parti della comunicazione, e prevede anche una serializzazione dei dati, ad esempio per linearizzare i dati strutturati come array o record. L'RPC supporta quattro semantiche: exactly once, at least once, at most once, zero or more.
Un'implementazione dell'RPC è Sun RPC, che prevede un programma in esecuzione sul server che contiene una o più procedure remote, che vivendo sullo stesso programma possono condividere variabili; inoltre più versioni dello stesso programma posso essere in esecuzione, quindi per invocare una procedura, il client avrò bisogno di una tripla (programma, versione, procedura). In base alla semantica, Sun RPC può essere TCP (exactly once, at most once) o UDP (at least once, zero or more). Di base con socket TCP/UDP bisogna concordare la porta su cui comunicare, ma Sun RPC usa il binding dinamico per il numero di porta, quindi il client deve prima contattare l'RPC port mapper, che ha una lista dei programmi attivi con rispettivo numero di porta, per ricevere la porta a cui comunicare (il port mapper è registrato sulla porta predefinita 111).
I middleware MOM (Message Oriented Middleware) sono basati su code di messaggi tra processi su rete, implementando il concetti di mailbox. In questo modello, la comunicazione non è client-server, ma peer-to-peer di tipo produttore consumatore asincrono: tramite un modello publish-subscribe, i produttori pubblicano i messaggi differenziati per tipo e i consumatori si iscrivono alla mailbox per riceverli.
Il modello a oggetti distribuiti (DOM) rappresenta la programmazione orientata agli oggetti applicata alla comunicazione client/server, cioè permette di invocare metodi su oggetti remoti come fossero locali, tramite un meccanismo analogo a quello RPC (procedure stub e un Interface Definition Language). Le piattaforme DOM si presentano spesso sotto forma di ORB (Object Request Brokers), ovvero una sorta di bus per la comunicazione tra oggetti su rete. Un esempio di DOM è Java RMI, che è specifico per Java (quindi ambiente distribuito omogeneo), dove i server creano oggetti e li registrano nell'RMI registry e i client li ricercano in questo catalogo e ne invocano i metodi. 

## gRPC
Il gRPC è un middleware universale, multilinguaggio e multipiattaforma che usa HTTP/2 per il trasporto e un protobuf come Interface Definition Language, per definire il contratto a cui le parti della comunicazione dovranno attenersi, supporta lo streaming bidirezionale, il multiplexing, l'autenticazione e le comunicazioni sia bloccanti che non.
L'idea di base è quella di trattare le procedure remote come fossero dei riferimenti a oggetti HTTP.
L'HTTP/2, rispetto all'1.1, fa uso di un Binary Framing Layer per suddividere le richieste/risposte HTTP in messaggi di piccola dimensione; questi messaggi poi vengono trasmessi in dei flussi (stream) bidirezionali che consentono di trasportare anche più di un messaggio alla volta, implementando così il multiplexing dato che un client non dovrà usare più di una connessione alla volta.
I protocol buffer (protobuf) di gRPC sono IDL che generano automaticamente stub client e classi server astratte da implementare; i messaggi vengono serializzati e trasmessi tramite HTTP/2. I tipi di dati definiti nei protobuf sono strutturati come messaggi, dove per messaggio si intende un record logico di informazioni contenute in una serie di campi (coppie nome-valore).
Ogni canale di comunicazione gRPC è thread-safe, così come lo sono gli stub lato client, solo il server è sempre soggetto al GIL.
gRPC supporta 4 tipi di RPC call: Semplice (il client invia una richiesta e riceve una risposta), Streaming lato server (il client invia una richiesta e riceve uno stream di risposte), Streaming lato client (il client invia uno stream di richieste e riceve una risposta), Streaming bidirezionale (il client invia uno stream di richieste e riceve uno stream di risposte).
Affinchè una funzione sia in grado di restituire uno stream, una classica return non va bene: bisogna usare una funzione Generator, che al posto di return usa yield, che ritorna un iteratore che che contiene n elementi su cui iterare.

## MOM
I message-oriented middleware sono utilizzati al posto di quelli basati su rpc, e sono ottimi per sistemi che richiedono scalabilità e disponibilità. La comunicazione è indiretta, quindi avviene tramite un intermediario che può essere, tra quelli che abbiamo visto, o una coda di messaggi (queue) o un publish-subscribe (topic). Il vantaggio dell'uso di un intermediario e che non c'è bisogno che tutte le parti della comunicazione siano in esecuzione contemporaneamente: un'applicazione A potrebbe inviare un messaggio al broker, che sarà poi ritirato da un'applicazione B quando questa entrerà in esecuzione  (comunicazione asincrona e disaccoppiamento, dato che sender non deve conoscere nulla del receiver e viceversa). Questo tipo di comunicazione è principalmente usato per la propagazione di eventi, tramite il pattern Observer.
Se il MOM fa uso di code di messaggi, in cui ogni messaggio ha un unico consumatore, si tratta di dominio Point-to-Point (PTP) in cui un messaggio viene conservato finché non è consumato (o finché non scade), se invece si parla di topic, allora il dominio è Publish-Subscribe, dove ogni messaggio può avere più consumatori e i messaggi sono conservati finché non sono rilasciati ai subscriber correnti.
Esistono vari protocolli utilizzati dai Broker MOM, quello che abbiamo visto noi è STOMP (Simple Text Oriented Message Protocol), tramite il broker Apache ActiveMQ. STOMP è un protocollo basato sullo scambio di STOMP Frames, tramite uno stream di messaggi. In Python si implementa tramite il modulo stomp. Per collegarsi al provider, si crea un oggetto connessione tramite stomp.connection(\[('ip', port)]) e in seguito si effettua la connect() sull'oggetto appena creato (specificando wait=True, si impedisce al programma di procedere finché la connessione non è stabilita). Per inviare messaggi si usa la send() sull'oggetto connessione, specificando la destinazione (/queue/... per il dominio PTP oppure /topic/... per il dominio Publish-Subscribe) e il messaggio da immettere nella mailbox. Per ricevere messaggi invece si chiama sulla connessione la set_listener(), specificando il nome del Listener e una classe che estende stomp.ConnectionListener e ridefinisce il metodo on_message(self, frame) (cioè il comportamento del Listener ogni volta che riceve un messaggio), e la subscribe(), specificando sempre la destinazione (Queue o Topic), un Id e il tipo di acknowledge (ad esempio, usiamo auto). Tramite STOMP si possono trasmettere i messaggi all'interno di una transazione, cioè i messaggi non verranno inviati alla mailbox finché la transazione non riceverà una commit() (oppure verranno scartati in caso di abort()).

## Web Services, REST e Flask
Un Web Service è un sistema identificato da un URI le cui interfacce pubbliche sono definite tramite XML. Un WS RESTful (REST sta per Representational State Transfer ed indica un'architettura in cui il sistema è aperto, a basso accoppiamento e distruibito massivamente) a differenza dei meccanismi RPC si basa sulle risorse (e non sulle procedure): il WS espone dati e funzioni tramite risorse identificate da URI, interagibili, nel caso di HTTP, tramite GET, POST, PUT e DELETE; è stateless, ovvero non esiste il concetto di sessione, ogni ciclo di richiesta-risposta è a se stante. Come anticipato, lo scenario più comune di un'architettura REST è sul protocollo HTTP, in cui ogni pagina è identificata da un URL e prevede i metodi visti prima per implementare le operazioni CRUD (Create, Retrieve, Update, Delete). XML e JSON sono formati usati per la rappresentazione testuale dei dati esterna.
A differenza di RPC, in cui ogni servizio espone un proprio "vocabolario", in REST il vocabolario è fisso: quello di HTTP. Per progettare un sistema REST bisogna prima identificare quali risorse esporre, e per ognuna definirne le URI, esporre un subset adeguato (ovvero definire il comportamento delle operazioni HTTP e quali sono ammesse su di essa) e progettarne le rappresentazioni (ad esempio in XML o JSON).
HTML è un linguaggio di markup ipertestuale, permette di strutturare visivamente gli elementi di una webapp; è composto da HTML tags, caratterizzati da opening e closing, al cui interno sono presenti testi o altri tag. Per i titoli o i contenuti importanti si usano i tag Header, per creare link si usa il tag Anchor e per specificare liste (ordinate e non) il tag List.
L'architettura definita dai tag HTML è detta Document Object Model (DOM, da non confondere con il Distributed Object Model): ogni tag rappresenta un DOM element e sono organizzabili come tree.
Un Web Framework è un insieme di tecnologie per lo sviluppo di Web App, quello che abbiamo visto noi è Flask, un microframework progettato per la realizzazione rapida e semplice di web app. Flask nasce come wrapper di Werkzeug (che mette a disposizione routing, debugging e WSGI) e Jinja2 (che mette a disposizione il supporto per i template).
I browser inviano richieste al web server che li instrada verso l'applicazione Flask, di conseguenza è necessario specificare quale codice eseguire in base all'URL richiesta: questo si fa tramite il decoratore @app.route(), sotto cui si specifica la funzione index() e di conseguenza la web app eseguirà quel codice alla richiesta di quell'URL. In Flask si possono definire anche dei dynamic routes, ovvero dei route che contengono porzioni variabili all'interno dell'URL (indicate con \<variabile\> e passate alla funzione come parametro: index(variabile)).
Di norma le view function (index()) ritornano stringhe generate direttamente al loro interno, ma per migliore comprensione e gestione del codice, conviene fare uso dei Template, forniti a Flask da Jinja2. Jinja2 è un template engine che fornisce i Template (ovvero la parte statica della risposta e dei placeholder per la parte dinamica) e il Rendering (che sostituisce i placeholder con i valori dinamici effettivi che possono essere qualsiasi tipo di variabile, anche tipi complessi come liste, dizionari o oggetti). Di default i template vanno messi nella sottocartella ./templates e sono file .html. Jinja2 offre anche delle strutture di controllo (condizioni e cicli). E' possibile generare richieste HTTP da terminale tramite il comando curl (con il parametro X si può specificare il metodo HTTP, con il parametro I si ottengono solo gli header della risorsa, con il parametro d si può specificare il campo data per le richieste POST e coon il parametro json si possono inviare dati in formato json per le POST). Un Request Object è ciò che mette a disposizione tutte le informazioni delle richieste HTTP inviate dai client. Attraverso il Request Object è possibile accedere al body della richiesta e ai parametri passati nella URL. Di default una route corrisponde a una richiesta GET, però si può usare l'argomento methods di route per definire altri metodi HTTP (ma Flask mette a disposizione dei metodi che fungono da shortcut per queste funzionalità, come @app.post()). Il valore di ritorno di una view function è convertito automaticamente in un Response Object (se è una stringa, conterrà la stringa come body, 200 come status code e text/html come mimetype; se è un dizionario o una lista viene usato automaticamente il metodo jsonify() per serializzare la risposta in json). Flask permette di costruire un Response Object all'interno della view function tramite la funzione make_response(), i cui argomenti vengono considerati come una tupla di valori per la generazione del Response Object.
In Pyton esiste una libreria HTTP per creare facilmente richieste HTTP, ovvero requests. I metodi principali sono head, get, post, put e delete. Il modulo requests consente di utilizzare le query string, cioè passare parametri all'interno dell'URL come keyword arguments. E' possibile popolare il payload del metodo post attraverso l'argomento data o json. Anche nel caso del modulo requests, il riferimento ottenuto dall'invio di una richiesta è un Response Object.

## NoSQL Datbases e MongoDB			
In generale i Database sono utilizzati sulla parte back-end delle Web App, permettendo di salvare persistentemente dati in memoria (riducendo così l'onere sulla memoria centrale). Un Database non è altro che una Collection di dati organizzati, accessibili tramite un DBMS, che fornisce la possibilità di creare, modificare e aggiornare database e dati. I Database possono essere di due categorie: Relazionali (SQL) e Non-Relazionali (NoSQL). Un Database SQL è composto di schemi, che forniscono un template su come vanno strutturate le tabelle dei dati, ad ogni tabella è associata una chiave primaria che consente l'identificazione univoca di un entità. In quanto ben strutturati, i DB SQL hanno pochi errori (anche grazie alle proprietà ACID), però questo è anche uno svantaggio, infatti risultano inutilizzabili per i big data, e inoltre è anche difficile gestire tabelle presenti su più server diversi.
I DB NoSQL invece sono più flessibili, infatti invece di tabelle fanno uso di collections di categorie diverse, in cui troviamo dei documents (le "righe della tabella"). Possono essere di più tipi, come key-value, document stores oppure search engines; quello che vediamo noi, MongoDB, è un Document Stores DB.
In questo tipo di DB, sono presenti delle collection che contengono document, ogni document può essere diverso, con un numero di campi variabile e senza necessità di uno schema predefinito. L'unica cosa richiesta è un campo \_id che dev'esserci in ogni document e rappresenta la chiave primaria del document. Ogni document è composto da field, ovvero coppie nome-valore.
Per usare MongoDB in Python si fa uso di PyMongo: si inizia effettuando la connessione all'istanza di MongoDB tramite il metodo MongoClient(ip, port),
da questo è poi possibile accedere ai database trattando la connessione come una collection, e in seguito è possibile accedere alle singole collection trattando il database stesso come collection. I dati in Python, in quanto JSON-style vengono trattati come dizionari.
Per l'inserimento di dati in una collection di un db si usano insert_one(dict) e insert_many(lista di dict); per la ricerca si usano find_one(filtro) e find(filtro) (che ritorna un cursor su cui iterare contenente gli elementi che rispettano il filtro), dove filtro rappresenta dei parametri (sempre sotto forma di dizionario, come ad esempio {"autore": "Eliot"}, ma è possibile anche usare degli operatori per le query più complesse); per la rimozione si usano delete_one(filtro) e delete_many(filtro); per l'aggiornamento si usano update_one(filtro, modificatore) e update_many(filtro, modificatore) dove il modificatore rappresenta l'aggiornamento da realizzare (esistono vari modificatori, come $set, $rename...).
