## Introduzione
L'uso di una virtual machine per simulare un sistema operativo comporta un onere prestazionale non indifferente, dovuto ai vari overhead presenti (hypervisor, sistema guest, ecc...), inoltre occupa grandi spazi di memoria e l'avvio non è dei più veloci. Il problema principale però è che esistono numerosissimi componenti applicativi, che, se gestiti tramite macchine virtuali o computer classici, richiedono configurazioni apposite in base all'ambiente necessario.
Un'alternativa alle macchine virtuali sono i Container, ovvero una forma di virtualizzazione leggera in cui non c'è emulazione dei dispositivi fisici, quindi l'overhead dell'hypervisor è nullo, ma bensì si fa uso dell'astrazione dei processi e della capacità di gestione delle risorse del sistema host, tramite Namespaces e Cgroups. In confronto ad una macchina virtuale, un container è decisamente più veloce ad avviarsi, e richiede conoscenze solo riguardo all'ambiente di esecuzione e il codice dell'applicazione (a differenza  di una VM che richiede conoscenze anche del sistema operativo guest). Inoltre è molto più leggero: su un singolo server fisico su cui è possibile far girare 100 VM, si possono far girare 1000 Container (di media), grazie ai pochi MB di dimensione dei dischi virtuali. L'uso di Container offre una soluzione al problema principale delle VM evidenziato prima: eseguendo i componenti applicativi in un Container, è possibile farne uso da praticamente qualsiasi hardware.

## Namespaces
Un Namespace è un dominio di denominazione di varie risorse, esistono di vari tipi, ad esempio mnt indica i mount point (i filesystem), pid i processi, net lo stack di rete, ipc per le Inter-Process Communication, uts per l'hostname e us1er per gli User ID. Tramite Namespaces, un Container agisce senza consapevolezza dell'astrazione, come se i programmi fossero in esecuzione su un sistema operativo, sarà poi il kernel, che riconosce che le system call derivano da un Container, a permettergli di accedere alle risorse collegati ai suoi Namespaces.
Le principali chiamate di sistema dei Namespace sono clone(), che crea un processo (ed un namespace se si specificano i flag CLONE_NEWxxx, dove xxx indica il tipo di Namespace); unshare() che non crea nuovi processi, ma è utilizzata per attaccare nuovi namespace al processo chiamante, sempre tramite l'uso di flag CLONE_NEWxxx e setns(), che permette di attaccare un namespace già esistente ad un container in esecuzione. 

## Cgroups
Il sottosistema Cgroups (control groups) è una soluzione per la gestione delle risorse. I moduli di Cgroups non si trovano in un'unica cartella, ma sono sparsi all'interno del kernel in base alla loro funzionalità. Tra i controller più rilevanti troviamo: memory, che definisce i limiti di uso di RAM da parte di un Cgroup; cpuset, che assegna processori e nodi di memoria ai Cgroups; net_prio, che permette di configurare il traffico di rete per ogni Cgroup; devices, che regola l'accesso ai dispositivi hardware da parte di un Cgroup; blkio, che regola l'uso della banda di input/output da e verso le memorie di massa; ecc...
In pratica, un Cgroup è un gruppo logico di processi che condividono le stesse regole, limitazioni e metriche per l'uso di risorse di sistema (date dai controller appena descritti), la cui traccia è tenuta e gestita dal kernel.

## Docker
Docker è un motore di container scritto in Go. Il suo funzionamento si basa su un'architettura Client-Server, dove il Client invia comandi da terminale per interagire con il DOCKER_HOST, ovvero il Server. Un Client in questo modo non ha bisogno di eseguire il container localmente, ma tramite comandi come docker build, pull e run, possono interfacciarsi con il motore Docker per istanziare dei container remoti. Il Server ha due risorse principali: i Containers, ovvero le istanze effettive in esecuzione e le Images, ovvero dei template pronti all'uso sulla base di cui lanciare dei container (nel caso in cui un Client richiedesse un template non presente, il DOCKER_HOST lo prenderà dal Registry, ovvero un repository esterno come Docker Hub).
I componenti principali usati dal motore Docker sono daemon, containerd, shim e runc. Il workflow è il seguente: viene eseguito un comando (ad esempio $docker container run . . .), e arriva tramite API REST una richiesta POST al daemon; successivamente il daemon comunica con containerd (ad esempio tramite gRPC) e gli delega la gestione del ciclo di vita del container, infatti lo scopo di containerd è proprio quello di gestire la logica di esecuzione di un container; inoltre viene istanziato un processo shim per ogni container in esecuzione, che ha la responsabilità di accogliere i processi generati dai runc e di mantenere aperti gli stream input/output finchè i rispettivi processi non terminano, tutto questo in maniera disaccoppiata da containerd, in modo che lui possa continuare a gestire la logica di esecuzione di altri container senza rallentarsi, ma soprattutto garantisce che un malfunzionamento sul daemon o sul containerd, non mandi in crash il singolo container, che continua a girare sul proprio shim; infine runc, citato prima, è il runtime di livello più basso, che lo scopo di interfacciarsi direttamente con il kernel (ad esempio, è lui a creare namespaces e cgroups), la sua caratteristica fondamentale è che non rimane in esecuzione dopo aver configurato e generato il processo principale del container (che, come detto prima, verrà accolto dall'apposito shim).
Un'immagine Docker non rappresenta un disco virtuale o un file system, ma bensì un entità di sola lettura, senza stato, rappresentata concretamente da un file compresso dotato di gerarchia: alla base troviamo il kernel host, su cui poggiano i layer dell'immagine, solitamente partendo da un'immagine base (ad esempio di una distribuzione di Debian), seguita da altri layer che rappresentano installazioni o istruzioni aggiuntive, fino ad arrivare al layer più alto, il container, che rappresenta l'unico strato scrivibile, ovvero ospita tutto ciò che viene creato, modificato e cancellato a runtime del container. Per far si che il container layer agisca come fosse un sistema operativo, docker usa uno Union File System, che unifica tutte le gerarchie e le directory presenti nell'immagine in un unico file system coerente. Lo Union File System utilizzato da Docker è OverlayFS.
Il Registry menzionato prima può essere di vari tipi: locale sull'host che esegue Docker; registro pubblico di Docker Hub oppure registri privati ma condivisi globalmente su docker.com.
